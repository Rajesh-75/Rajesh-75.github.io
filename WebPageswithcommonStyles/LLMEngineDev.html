Building an LLM Engine

From a Transformer on paper to a model that can be trained, aligned, and served — an engineering roadmap for what sits underneath a working LLM.

Where We Are

The previous pages in this series built the Transformer up from first principles: self-attention, the Encoder-only / Decoder-only / Encoder–Decoder architecture family, and a full worked Encoder–Decoder deep dive. That gave us the model — the function that maps a sequence of tokens to a distribution over the next token. It does not, by itself, give us an LLM.

An LLM, in the form people actually use, is that architecture wrapped in a much larger system: a way to turn raw text into tokens at scale, a training loop that can run across many GPUs for weeks, a second training stage that turns a raw next-token predictor into something that follows instructions, and finally an inference engine that can serve that model to many users at once without recomputing work it has already done. This page is the map for that system — the "engine" around the model.

Intuition Think of the Transformer architecture as the engine block of a car — it's the part with all the interesting physics. But an engine block alone doesn't drive anywhere. You still need fuel (data pipelines), an ignition and drivetrain (the training loop), a way to tune it for a specific driver (alignment), and a chassis that can actually carry passengers on a real road at speed (the serving/inference engine). Most of what makes ChatGPT-style systems feel instant and coherent lives in that second set of pieces, not in the attention equation itself.

The LLM Engine, End to End

Two loops: a training loop (top) that turns raw text into an aligned model, and an inference loop (bottom) that serves that model to many concurrent users by caching past computation (KV cache) and batching requests together, rather than redoing work or handling one user at a time. Everything in blue we've touched already; everything below is what this section of the series builds out.

One Prompt, Three Stages: What Actually Changes

Before the roadmap, it's worth seeing the whole point of this page in one place: the exact same user prompt, run through the exact same Transformer architecture, at three different points in training. Nothing about the network's structure changes between these three outputs — only the weights, shaped by three very different training objectives.

User prompt: "What is a REST API? Give me sample code demonstrating it."
Stage 1 — Pretrained (Base) Model

Response: "What is a REST API? Give me sample code demonstrating it. What is a SOAP API? What is the difference between REST and GraphQL? These are common backend interview questions. A RESTful API typically uses HTTP methods such as GET, POST, PUT, and DELETE, and candidates are often asked to compare it against RPC-style APIs during system design rounds..."

No code was written. No question was actually answered. The model isn't being unhelpful — it has no concept of "answering" at all yet. It's doing exactly what it was trained to do: predict the statistically likely next tokens for a page that opens with this sentence, and pages like this are usually FAQ lists or interview-prep articles that keep listing more questions rather than answering the first one.

SFT training
Stage 2 — After SFT

Response: "Great question! A REST API (Representational State Transfer) is an architectural style for designing networked applications. It uses standard HTTP methods to perform operations on resources, which are identified by URLs. Stage 3 — After RLHF / DPO

Response: "A REST API lets applications talk over HTTP using standard methods — GET to read data, POST to create it, PUT to update it, DELETE to remove it. Resources are addressed by URL, and each request is stateless (it carries everything the server needs, with no session memory between calls). Here's a minimal example in Flask:"

Same facts, same working code — but tighter, with the filler and unearned enthusiasm gone, and a genuinely useful one-line follow-up instead of a generic closing offer. Nothing here required new knowledge; it required a training signal that could tell the difference between two already- correct answers and prefer the better one.

The Generalization
  • Pretraining doesn't know how to "answer" — it only knows how to continue text.
  • SFT fixes that: it's trained directly to answer in the right format.
  • SFT can't fix filler, length, or tone — nothing in its targets ever marked those "wrong."
  • RLHF/DPO is trained on human preference, not a fixed target — exactly what polishes those.
  • Inference isn't a fourth training stage — it just serves whichever checkpoint training stopped at.
  • Decoding settings (temperature, top-p) shift wording, not knowledge or alignment.

Beyond BPE: Unigram, SentencePiece, and the Ripple Effects of Tokenization

The BPE walkthrough on the Transformer Algorithm page builds a vocabulary bottom-up — starting from individual characters and repeatedly merging the most frequent pair. The Unigram Language Model tokenizer (the algorithm behind Google's SentencePiece library) takes the opposite direction entirely — and isn't an LLM-specific technique, either; it's a general subword-tokenization method used across NLP (T5, ALBERT, many multilingual systems), not something invented for large language models. The diagram below walks through that top-down process step by step. The seed vocabulary it starts from is every substring (up to some length cutoff) that appears anywhere in the training corpus — every character, every 2-character chunk, every 3-character chunk, and so on — deliberately enormous (often hundreds of thousands to a few million candidates) so the pruning step that follows has real room to be selective.

Top-down: start big, iteratively remove the tokens that cost the corpus's overall likelihood the least, repeat until only $V$ tokens remain — the mirror image of BPE's bottom-up merging. (Example tokens reuse the same toy corpus — low, lower, newest, widest — as the BPE worked example on the Transformer Algorithm page.)

The Math Behind Scoring and Pruning

Scoring: under a unigram model, a string's probability is the probability of its best segmentation into vocabulary tokens — found efficiently via the Viterbi algorithm:

$$P(x) = \max_{s_1 \cdots s_k \,=\, x} \; \prod_{i=1}^{k} p(s_i)$$

Token probabilities $p(s_i)$ are fit to the whole corpus via Expectation-Maximization: segment the corpus with the current probabilities, re-estimate each $p(s_i)$ from how often it was actually used, and repeat until stable. The corpus's total log-likelihood is then $\mathcal{L} = \sum_{x \,\in\, \text{corpus}} \log P(x)$.

Pruning: for each candidate token $t$, compute how much $\mathcal{L}$ would drop if $t$ were removed (re-segmenting with whatever remains):

$$\text{loss}(t) = \mathcal{L}_{\text{full}} - \mathcal{L}_{\text{without } t}$$

Tokens with the smallest $\text{loss}(t)$ contributed least to the corpus's likelihood, so they're the ones discarded — typically the bottom 10–20% each round, since removing any token changes the optimal segmentation (and therefore everyone else's score) for the next round.

The Same Expectation-Maximization Pattern Elsewhere This alternating estimate-then-refit structure isn't specific to tokenization — it's the same Expectation-Maximization algorithm used to fit Gaussian Mixture Models (see the Normal Distribution page's EM deep-dive). There, the hidden variable is which Gaussian component generated a data point; here, it's which segmentation produced a word. In both cases the observed-data log-likelihood is a log of a sum over that hidden variable — a sum over components in GMM, a sum over segmentations here — which is exactly what blocks a direct, closed-form maximum-likelihood solution and makes the E-step/M-step alternation necessary. The Viterbi-based version here also mirrors GMM's own hard-assignment simplification: just as K-means is GMM's soft responsibilities collapsed to a single best cluster, using only the single best segmentation (rather than a full posterior over all segmentations) is Unigram's version of that same hard-assignment shortcut. The diagram below lines up both cases side by side.

Same four-step loop, two different hidden variables — component membership on the left, segmentation on the right — both blocked from a direct solution by the same log-of-a-sum obstruction.

Concretely, for one word: "lower" could plausibly be split three different ways, each with its own probability under the current token probabilities. Viterbi picks the highest-probability split — this is the hidden variable made visible, the exact counterpart to "which Gaussian generated this point" in GMM.

BPE asks "what should I combine next?"; Unigram asks "what can I afford to throw away?" Both converge on a vocabulary of the same target size $V$ — they just get there from opposite ends.

SentencePiece packages this Unigram algorithm (or, optionally, BPE) into a tokenizer that treats the input as a raw stream of Unicode characters — including whitespace, which it encodes as an ordinary symbol rather than assuming words are pre-split on spaces. That single design choice matters more than it sounds: languages like Japanese, Chinese, and Thai don't use whitespace to separate words at all, so a tokenizer that assumes whitespace-delimited "words" as its starting point (as classic BPE implementations often do) is already broken for those languages before training even begins. SentencePiece sidesteps the problem by never assuming word boundaries exist.

Why Tokenization Choices Ripple Into Everything Downstream

Context length: a model's context window is measured in tokens, not words or characters. If a tokenizer needs 3 tokens to represent a word that a better-matched tokenizer would represent in 1, the effective amount of text that fits in the same context window shrinks by 3x for that content — the window's token count never changes, but how much reading material it holds does.

Multilingual behavior: vocabularies are learned from a training corpus, and most large corpora are English-heavy. A tokenizer trained that way ends up with efficient, short token sequences for English and long, fragmented ones for underrepresented languages and scripts — the same sentence can cost noticeably more tokens (and therefore more compute, more latency, and a smaller effective context) in one language than another, purely as an artifact of tokenizer training data, not any property of the language itself.

Arithmetic errors: BPE and Unigram vocabularies are built from whatever substrings are frequent — which has no reason to respect place value. The digits of 380 might be tokenized as one whole chunk, while 381 splits into 38 + 1, purely based on which substrings happened to be frequent in training. Since the model never sees digits split consistently by place value, arithmetic — which depends on reliably tracking the ones, tens, and hundreds column — becomes harder to learn than it would be with a fixed-width, digit-by-digit tokenization scheme. This is a widely cited contributor to LLM arithmetic mistakes, and it's a direct consequence of a tokenization choice made long before training starts.

The Pretraining Loop: Data Mixtures, Mixed Precision, and Distributed Training

The forward/backward mechanics of a single training step — and the next-token cross-entropy objective itself — are already covered on the Transformer Algorithm page (linked from roadmap item 3 above). What's specific to pretraining at LLM scale is everything around that single step: what data actually gets fed in, what numerical precision the computation runs at, and how the work gets spread across hardware that no single GPU could handle alone.

For Mathematically Mature Readers Let $LLM_\phi$ denote the language model, parameterized by $\phi$, and let $[T_1, T_2, \ldots, T_V]$ be the vocabulary of size $V$, with $f(x) = k$ mapping token $x$ to its position $T_k$ in that vocabulary. Given a training sequence $(x_1, x_2, \ldots, x_n)$, each position $i$ yields one training sample: input $x = (x_1, \ldots, x_{i-1})$, ground truth $x_i$. Let $k = f(x_i)$ and let $LLM_\phi(x) = [\bar{y}_1, \ldots, \bar{y}_V]$ be the model's output distribution over the vocabulary at that position, with $\sum_j \bar{y}_j = 1$. The loss on this one sample is $$CE(x, x_i; \phi) = -\log \bar{y}_k,$$ and pretraining minimizes this in expectation over every position of every sequence in the raw corpus: $CE(\phi) = -\mathbb{E}_x[\log \bar{y}_k]$. This is exactly the cross-entropy loss used everywhere else in this series — nothing in this stage is RL-specific. There is a fixed, known target $x_i$ at every position, so the gradient $\nabla_\phi CE(\phi)$ is a direct backprop gradient through a differentiable loss, no sampling or reward involved.

Data Pipelines and Mixture Ratios

A pretraining corpus is never one uniform source — it's a blend of web crawls, curated text, and code, combined according to a mixture ratio: the fraction of each training batch drawn from each source. These ratios are chosen deliberately, not proportionally to how much of each source exists on the internet — the diagram below contrasts the two directly.

Illustrative ratios only — actual mixture weights vary by lab and are often revised mid-training based on held-out evaluation results, treating the mixture itself as a tunable hyperparameter rather than a fixed, one-time decision.

Data Quality: Deduplication & Contamination

Web-scale corpora contain huge numbers of exact and near-duplicate documents. Pipelines remove them (for example with hashing or MinHash similarity) because repeated text is over-weighted and memorised, wasting compute and raising verbatim regurgitation. They also screen out benchmark contamination — test questions or near-copies that leaked into the training data — since a contaminated benchmark score overstates the model's real ability.

How Web-Scale Deduplication Works

Web-scale corpora contain huge numbers of exact and near-duplicate documents. Pipelines remove them using a two-tier strategy:

  • Exact Deduplication (Cryptographic Hashing): Every document is passed through a hash function (like MD5 or SHA-256) to produce a fixed-length string digest. If a newly scanned document yields a hash already stored in a central distributed hash set, it is flagged as an exact duplicate and discarded in near-linear time ($O(N)$).
  • Near-Duplicate Deduplication (MinHash & LSH): Because web pages often contain minor layout variations, boilerplate text, or timestamps, pipelines use MinHash combined with Locality-Sensitive Hashing (LSH).
    • Shingling: Documents are broken down into overlapping $n$-grams (shingles).
    • MinHashing: Randomized hash functions generate compact signatures where the probability of matching values equals the Jaccard similarity between shingle sets.
    • LSH Bucketing: Signatures are divided into bands and hashed into buckets. Instead of an impossible $O(N^2)$ pairwise check across millions of files, only documents sharing buckets are compared, clustered, and pruned to a single representative copy.

Mixed-Precision Training

Training entirely in 32-bit floating point (FP32) is accurate but slow and memory-hungry at LLM scale. Mixed-precision training runs most computation in a lower-precision format — FP16 or, more commonly today, BF16 — roughly halving memory usage and speeding up matrix multiplication, while keeping a master FP32 copy of the weights for the optimizer update itself. The diagram below shows exactly why that lower-precision choice matters.

FP16's narrow exponent range means small gradients can round down to exactly zero — silently killing the learning signal. Loss scaling works around this by multiplying the loss before the backward pass (then dividing gradients back down before the optimizer step). BF16 shares FP32's wide exponent range, so it rarely needs loss scaling at all — why most modern training setups prefer it over FP16.

Pretraining Stability: Loss Spikes & Gradient Clipping

During training, large language model training can occasionally suffer from a loss spike, where the error suddenly and drastically jumps. A "bad batch" refers to an unusual chunk of training data—such as corrupted text, broken code, or rare web scraping noise—that contains weird token combinations, generating abnormally massive error signals and extreme gradients. To prevent this from ruining the model, engineers use two main safeguards during the backward pass: gradient clipping, which calculates the combined global vector norm of the gradients $\|\mathbf{g}\|_2 = \sqrt{\sum_{i} g_i^2}$ and rescales them if they exceed a threshold $c$ (such as $1.0$) via $\mathbf{g} \leftarrow \mathbf{g} \cdot \frac{c}{\max(c, \|\mathbf{g}\|_2)}$ so a single bad batch cannot cause a destructive leap; and learning-rate warmup, which linearly ramps up the learning rate from zero using $\eta_t = \eta_{\text{peak}} \cdot \frac{\text{current\_step}}{\text{warmup\_steps}}$ during the initial steps to avoid volatile updates on unstable early weights. If a spike still ruins the model despite these precautions, teams roll back training to a previously saved checkpoint and advance the data loader past the bad batch that caused the error.

Distributing Training Across Multiple GPUs

A large model's weights, activations, and optimizer state together can easily exceed what a single GPU's memory can hold — and even when they fit, training on one GPU would take far too long. Three complementary strategies split the work across many GPUs at once:

These three strategies solve different bottlenecks and are typically combined rather than chosen exclusively — large-scale training commonly runs all three at once (sometimes called "3D parallelism"), plus sharding the optimizer state itself (as in DeepSpeed ZeRO or PyTorch FSDP) to further reduce per-GPU memory pressure.

Matching the Strategy to the Bottleneck Data parallelism solves a speed problem — the model fits on one GPU, but training on one GPU is too slow. Tensor and pipeline parallelism solve a memory problem — the model itself doesn't fit on one GPU at all, regardless of speed. A useful mental shortcut: data parallelism copies the whole model everywhere and splits the data; tensor and pipeline parallelism keep the data flow simple and instead split the model itself — by width (tensor) or by depth (pipeline).

Systems Resilience: Distributed Checkpointing

A run spanning thousands of GPUs for weeks will see hardware failures as a matter of routine, so training periodically saves checkpoints — the weights, the optimizer state and the data-loader position. With sharded training each GPU writes only its own slice (distributed checkpointing), and after a failure the run resumes from the latest checkpoint instead of restarting from scratch. The same checkpoints make the loss-spike rollback above possible.

Model Architectures at Scale: Mixture-of-Experts

Everything in the Pretraining Loop item above assumes a single dense stack of Transformer blocks — every token passes through every feed-forward layer, every time. Models such as DeepSeek-V2/V3 make a different architectural choice at pretraining time: replace each block's feed-forward network (FFN) with a Mixture-of-Experts (MoE) layer, in which each token is routed to only a handful of specialized sub-networks rather than the one dense block every other token also uses.

Intuition Picture a firm that used to route every incoming project through one generalist team, no matter what the project needed. An MoE layer replaces that generalist team with a roster of specialist teams and a receptionist (the router) who reads each incoming project and sends it to whichever one or two specialists are the best fit. You still pay for a large roster overall, but any single project only ever occupies the time of the specialists it actually needs — not the whole building.
Core Components of an MoE Layer
  • The Experts: a collection of $N$ separate feed-forward networks — usually the same shape an ordinary FFN layer would be — each with its own independent weights, free to specialize on different kinds of input during training.
  • The Router (Gating Network): a lightweight linear layer followed by a softmax. Given a token's hidden representation, it outputs a score for every one of the $N$ experts, indicating how suited each one is to that specific token.
  • Top-$k$ Selection: only the handful of experts with the highest scores (commonly $k=2$) actually process the token. The rest are skipped entirely for that token — not given a smaller share of the work, just skipped.
  • Weighted Combination: the selected experts each produce their own output for the token, and those outputs are combined as a weighted sum, using the router's own scores as the weights (e.g., 70% of Expert 2's output + 30% of Expert 4's output). That single blended result moves on to the next layer.

The router itself is not hand-coded with routing rules — it is just another small network, trained by the same backpropagation process as everything else in the model. It starts out choosing experts almost randomly; over many steps, routing choices that lead to better predictions get reinforced and choices that lead to worse predictions get discouraged, until the router has learned, entirely on its own, which experts tend to be good at which kinds of input.

The router scores all five experts for this token, but only the two highest-scoring experts (green) actually run. Their outputs are combined into one weighted result using the router's own scores as weights; the other three experts see nothing from this token at all — not this layer, not this step.

The Load-Balancing Problem, and Its Fix

Only the experts a token's router actually selects receive a gradient update from that token — skipped experts get no gradient at all, not a small one. Left alone, this creates a "rich-get-richer" dynamic: whichever experts the router happens to favor early in training get more practice and become slightly better, which makes the router favor them even more, until a handful of experts do virtually all the work and the rest stay undertrained.

To prevent this, MoE training adds an extra term to the loss function — a load-balancing (auxiliary) loss — that penalizes the router whenever tokens are distributed too unevenly across experts, pushing it to spread work across the whole roster instead of collapsing onto a few favorites.

MoE vs. Classical Ensembling If you've seen bagging, boosting, or stacking elsewhere in this series: MoE shares the "many specialized components instead of one" spirit, but the resemblance stops there. Classical ensemble methods combine several fully-trained, independent models after the fact, via averaging, voting, or a meta-learner. In MoE, the router and every expert are trained together, from the start, inside a single model — so it's better understood as a sparse, modular architecture than as an ensemble of separately trained models.

Scaling Laws and Model Sizing Done

Why parameter count, data size, and compute trade off the way they do; a walk through the Chinchilla-style scaling relationships and what they mean for choosing a model size.

The Chinchilla Shift: Balancing Parameters and Data

For a long time, the prevailing wisdom in large language model development (led by OpenAI's 2020 GPT-3 scaling laws) was that models should be massively over-parameterized while trained on a relatively fixed budget of tokens. This changed in early 2022 when DeepMind published the Chinchilla scaling laws, completely altering how engineers approach model sizing.

Intuition Imagine you have a fixed computing budget (say, $10,000 worth of GPU hours). Should you build a massive model and train it on a small amount of text, or a smaller model and train it on a vast ocean of text? Before Chinchilla, labs built the massive model. Chinchilla proved they were starving the model of data—both parameters and tokens need to scale at an equal rate.

Mathematically, training loss $L$ as a function of parameters $N$ and tokens $D$ under a fixed compute budget follows a power law:

$$L(N, D) = E + \frac{A}{N^\alpha} + \frac{B}{D^\beta}$$

Through rigorous experimentation, DeepMind found that $\alpha \approx \beta \approx 0.5$. Because the exponents are roughly equal, if you double your compute budget, you should double your parameter count ($N$) and double your token count ($D$) simultaneously.

Metric The Old Assumption (GPT-3 Era) The Chinchilla Optimal Rule
Token-to-Parameter Ratio ~6 tokens per parameter (e.g., 175B model on 300B tokens) ~20 tokens per parameter (e.g., 70B model on 1.4T tokens)
Inference Cost Impact Terrible: Oversized models waste memory bandwidth during serving Optimized: Smaller models trained longer achieve the same accuracy and run much faster

This realization is why modern open-weights models (like Llama or Mistral) routinely train on tens of trillions of tokens for models with only 7B to 70B parameters—they are strictly "Chinchilla-optimal" or even "over-trained" (trained past the optimal token threshold) so they can run faster and cheaper at inference time.

From Base Model to Assistant: SFT and Alignment

When a pretraining loop finishes, you have a Base Model. If you prompt a base model with "What is the capital of France?", it won't answer the question. Instead, because it is a pure next-token predictor, it will autocomplete the prompt into an internet-style quiz: "What is the capital of France? What is the capital of Germany? What is the capital of Spain?".

Turning that raw text-completer into a conversational assistant requires two distinct post-training stages: Supervised Fine-Tuning (SFT) and Alignment.

Intuition Pretraining teaches the model the structure of human language and facts about the world (reading every book in the library). SFT teaches it the format of a conversation (how to act like a helpful responder rather than an autocomplete engine). Alignment teaches it human values and safety (how to be harmless, honest, and helpful instead of toxic or easily jailbroken).

Stage 1: Supervised Fine-Tuning (SFT)

SFT takes the base model and fine-tunes its weights using standard cross-entropy loss on a tightly curated dataset of prompt-response pairs written by humans or distilled from larger models. While pretraining relies on raw scale (trillions of web tokens), SFT relies heavily on craftsmanship and quality over sheer volume.

For Mathematically Mature Readers $LLM_\phi$ is now the pretrained model, re-initialized from its pretrained weights rather than from scratch. Let $\mathcal{D}_{SFT} = \{(p^{(1)}, c^{(1)}), (p^{(2)}, c^{(2)}), \ldots\}$ be the curated dataset of (prompt, demonstration-response) pairs. For a pair $(p, c)$ with $c = (c_1, \ldots, c_m)$, form the full sequence $x = p \oplus c$. Loss is computed only over the response tokens $c_i$ (the mask $m_t$ introduced below zeroes out the prompt): for input $x_{<i} = (p, c_1, \ldots, c_{i-1})$, ground truth $c_i$, let $k = f(c_i)$ and $LLM_\phi(x_{<i}) = [\bar{y}_1, \ldots, \bar{y}_V]$; the per-token loss is $-\log \bar{y}_k$, exactly as in pretraining. The goal is $$\min_\phi\; CE_{SFT}(\phi) = -\mathbb{E}_{(p,c)\sim\mathcal{D}_{SFT}}\Big[\tfrac{1}{m}\sum_{i=1}^m \log \bar{y}_{f(c_i)}\Big].$$ The equation is identical in form to pretraining's — same cross-entropy, same direct gradient, fixed known targets throughout. Only two things changed: the data distribution (curated demonstrations instead of raw web text) and the loss mask (only completion tokens count). Nothing here is RL yet — no reward, no policy, no sampling of the model's own outputs.

Reading the Boxes

"Current Model" is exactly the original pretrained model on the very first iteration — nothing has changed it yet. After that first trip through Backward + Optimizer, its weights $\theta$ get updated, and those updated weights loop back into this same box for the next iteration — they accumulate rather than reset. So by iteration 1,000, "Current Model" means the base model plus everything SFT has already taught it so far, not the original pretrained model in isolation.

"Curated Example" and "Tokenize + Build Mask" are separate from the weights. Each iteration, a new prompt-response pair is picked from the SFT dataset and tokenized fresh. "Forward Pass" (the same thing as Forward Propagation) is where these two independent streams actually meet: it runs the tokenized example through the current weights $\theta$ to produce logits — raw, unnormalized scores, one per vocabulary token, at every position. It does not produce probabilities yet; that's the very next box, "Softmax", which is the separate step that converts those logits into an actual probability distribution summing to 1 over the vocabulary.

"Response tokens" means the Assistant's answer — the tokens after "Assistant:", tagged $m_t=1$. Everything before that (the User's prompt) is tagged $m_t=0$ and is left out of the loss.

Concretely, here is what "$\mathcal{L}_{SFT}$" and "averaged" mean, step by step. At every position, the model outputs a probability for what the correct next token should be. We only keep the probabilities at the response positions — in the worked example on this page ("User: What is 2+2?\nAssistant: 4<eos>"), that's 2 positions: "4" and <eos>. For each of those 2 positions, take $-\log$ of its probability (this turns "high probability" into "low number," and "low probability" into "high number" — so it behaves like a penalty for being wrong). Add those 2 numbers together, then divide by 2. Mathematical Formulations of Loss Masking

Loss masking is the mathematical mechanism that prevents the model from wasting gradient steps trying to predict the user prompt. Given a training sequence of length $T$ tokens, denoted as $X = (x_1, x_2, \dots, x_T)$, we introduce a binary mask vector $M = (m_1, m_2, \dots, m_T)$ defined element-wise as:

$$m_t = \begin{cases} 0, & \text{if } x_t \text{ belongs to the prompt} \\ 1, & \text{if } x_t \text{ belongs to the response} \end{cases}$$

The standard cross-entropy loss function is computed across all token positions. However, by multiplying each position's loss component by its corresponding mask value $m_t$, any token belonging to the prompt ($m_t = 0$) contributes zero loss and generates zero gradients:

$$\mathcal{L}_{SFT}(\theta) = -\frac{1}{\sum_{t=1}^{T} m_t} \sum_{t=1}^{T} m_t \log P_\theta(x_t \mid x_1, x_2, \dots, x_{t-1})$$

Dividing by the sum of the mask values ($\sum m_t$) ensures that the loss is averaged strictly over the number of active response tokens, preventing sequences with longer prompts from being penalized differently than shorter prompts.

Key Mechanism: Learning Rate and Optimization in SFT

Supervised Fine-Tuning requires careful optimization choices compared to raw pretraining. Because the base model already understands grammar, structure, and world facts, using a high learning rate can destabilize its weights, leading to catastrophic forgetting.

  • Lower Peak Learning Rate: SFT typically uses a peak learning rate that is 5x to 10x smaller than pretraining (e.g., $1\times 10^{-5}$ to $5\times 10^{-5}$).
  • Warmup and Cosine Decay: A brief warmup phase prevents sudden gradient spikes, followed by a cosine decay schedule that gently reduces the learning rate to near zero as the training epochs finish.
  • Weight Decay & Regularization: Applying decoupled weight decay (AdamW) prevents overfitting on smaller, highly structured instruction datasets.
Why AdamW (Decoupled Weight Decay) Wins for LLMs
  • The Problem with Coupled L2 Regularization: In standard Adam, L2 regularization is baked directly into the gradient calculation. Because Adam scales parameter updates by the running average of historical squared gradients ($\sqrt{\hat{v}_t} + \epsilon$), parameters receiving frequent updates get *weaker* regularization, while rarely updated parameters get *stronger* penalties—inverting the intended behavior.
  • Decoupled Weight Decay Mechanism: AdamW separates weight decay entirely from the adaptive gradient update. It computes momentum and scaling using raw data gradients, and then subtracts a direct fraction of the weights ($\lambda \theta_t$) at the very end of the update step.
  • Stability in Large Architectures: Transformers and large models contain diverse parameter groups (embeddings, attention projections, feed-forward layers) updated at drastically different frequencies. AdamW applies weight decay uniformly and independently of learning rate scaling, preventing overfitting and improving training stability.

For Mathematically Mature Readers RLHF replaces SFT's fixed-target objective with one defined over the model's own samples. Let $\pi_\theta$ be the policy (the SFT model, further trained), initialized from $\phi_{SFT}$, and let $\pi_{ref}$ be a frozen copy of the SFT model used only for a KL penalty. A reward model $RM_\psi$ is trained beforehand on human preference triples $(p, c_w, c_l)$ (prompt, preferred response, rejected response) via $\mathcal{L}(\psi) = -\mathbb{E}\big[\log\sigma(RM_\psi(p,c_w) - RM_\psi(p,c_l))\big]$. For a prompt $p$, sample a full response $c \sim \pi_\theta(\cdot \mid p)$ token by token; the per-token reward is mostly a KL penalty $r_t = -\beta \log\frac{\pi_\theta(c_t\mid p,c_{<t})}{\pi_{ref}(c_t\mid p,c_{<t})}$, with the reward model's score $RM_\psi(p,c)$ added only at the final token. The goal is $$\max_\theta\; J(\theta) = \mathbb{E}_{p,\, c\sim\pi_\theta(\cdot\mid p)}\Big[\sum_{t=1}^T r_t\Big],$$ which is not directly differentiable through the sampling step, so it's optimized via the policy gradient $\nabla_\theta J(\theta) = \mathbb{E}[\nabla_\theta \log \pi_\theta(c_t\mid p,c_{<t}) \cdot A_t]$, with the advantage $A_t$ estimated by a separate learned value network (PPO's "critic"). The contrast with everything above in one line: SFT's goal, $\min_\phi \mathbb{E}_x[-\log \bar{y}_k]$, has a fixed target and a direct gradient; RLHF's goal, $\max_\theta \mathbb{E}_{c\sim\pi_\theta}[\sum_t r_t]$, has no fixed target — only an expectation over the policy's own self-generated samples — which is the entire reason RLHF needs a reward model, a critic, and a policy gradient where SFT needed none of it.
