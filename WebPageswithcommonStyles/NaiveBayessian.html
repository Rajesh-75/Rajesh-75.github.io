7 Bayes' Theorem: Prior, Likelihood, and Posterior

Definitions

Prior — P(A): What we believe about A before seeing any new evidence. It reflects existing knowledge, historical frequency, or assumption — essentially our starting belief.

Likelihood — P(B|A): How probable the observed evidence B is, assuming A is true. It measures how well a given hypothesis explains the data we just observed.

Posterior — P(A|B): Our updated belief about A after incorporating the new evidence B. This is the quantity we actually care about — it combines what we already knew with what we just observed.

The relation:

$$\text{Posterior} \propto \text{Prior} \times \text{Likelihood}$$

In words: start with what you believed, adjust it by how well the new evidence supports that belief, and arrive at an updated, more informed belief.

Intuitive Example 1: Box of Colored Balls

Imagine two boxes:

  • Box A contains 8 red balls and 2 blue balls.
  • Box B contains 3 red balls and 7 blue balls.

You pick a box at random (50/50 chance — this is your prior, P(Box A) = P(Box B) = 0.5), then draw one ball without looking, and it turns out to be red.

Now you ask: given that I drew a red ball, which box did I likely pick from?

  • Likelihood P(red | Box A) = 8/10 = 0.8 — red balls are common in Box A.
  • Likelihood P(red | Box B) = 3/10 = 0.3 — red balls are rare in Box B.

Multiplying prior × likelihood for each box:

  • Box A: 0.5 × 0.8 = 0.4
  • Box B: 0.5 × 0.3 = 0.15

Even though you started with equal belief in both boxes, observing a red ball shifts your posterior belief strongly toward Box A. This is the entire mechanism behind Bayesian reasoning — evidence reshapes prior belief into a posterior belief, and the shift is proportional to how well each hypothesis "explains" what you saw.

Intuitive Example 2: Image Processing (Pixel Classification)

Suppose you're building a system to classify a pixel as "skin" or "not skin" in an image (a classic early computer vision task, before deep learning dominated).

  • Prior: P(skin) — what fraction of pixels in typical photos are skin-colored, based on general experience (say, 20%).
  • Likelihood: P(pixel's RGB value | skin) — given that a pixel IS skin, how likely is it to have this specific color? Skin tones cluster in a fairly predictable RGB range, so this likelihood is high for skin-like colors and low for, say, bright green pixels.
  • Posterior: P(skin | observed RGB value) — after seeing the actual pixel color, what's the updated probability it's skin?

If a pixel's color strongly matches typical skin-tone statistics, the likelihood term dominates and pushes the posterior high — even if skin pixels are relatively rare overall (low prior). This mirrors exactly how Naive Bayes text classification works later in this tutorial: instead of pixel colors, you'll see word occurrences updating the posterior probability of a class (e.g., spam vs. not-spam).

How This Inspired Classification Learning

Bayes' theorem gives a natural, principled way to answer the core question of classification: given the features I observe, which class is most probable?

$$P(\text{class} \mid \text{features}) \propto P(\text{class}) \times P(\text{features} \mid \text{class})$$

This reframes classification as a belief-updating problem: start with how common each class is in general (prior), then ask how well the observed features match each class's typical pattern (likelihood), and combine the two to get an updated, evidence-informed probability for each class (posterior). The predicted class is simply the one with the highest posterior.

Why We Can't Use This Relation Directly for Classification

The formula above looks simple, but there's a serious practical obstacle hiding inside the likelihood term: P(features | class) means the joint probability of every feature occurring together, given the class. In the pixel example, that was manageable because we only had one feature (RGB color). But real classification problems — like a text document — have dozens, hundreds, or thousands of features (every word position, every pixel, every sensor reading), and estimating their joint distribution directly requires accounting for every possible combination and correlation between them simultaneously.

This is computationally and statistically intractable for two reasons:

  1. Combinatorial explosion — the number of possible feature combinations grows exponentially with the number of features, so you'd need an enormous (often impossible) amount of training data to reliably estimate probabilities for every combination.
  2. Data sparsity — with realistic dataset sizes, most specific feature combinations will simply never appear in training data at all, making their joint probability impossible to estimate from counts.

The Approach Used Instead: The "Naive" Independence Assumption

To make this tractable, Naive Bayes introduces a simplifying assumption: treat every feature as conditionally independent of every other feature, given the class. Instead of estimating one enormous joint probability, this lets you break the likelihood into a product of small, individually estimable pieces:

$$P(\text{features} \mid \text{class}) \approx P(f_1 \mid \text{class}) \times P(f_2 \mid \text{class}) \times \dots \times P(f_n \mid \text{class})$$

This is why it's called "Naive" Bayes — the independence assumption is almost never perfectly true in reality (word choices in a sentence are correlated, pixel colors do depend on neighboring pixels), but it makes the math solvable with a small, fixed amount of data per feature rather than an exponential amount of data per feature combination. It trades some accuracy for tractability.

How the Algorithm Is Actually Built From This Assumption

Once the joint likelihood is broken into a product of individual, per-feature likelihoods, the entire Naive Bayes algorithm falls directly out of that one simplification — every step below exists purely to exploit the fact that each feature can now be handled separately rather than jointly.

1. Training becomes "estimate small, separate pieces" instead of "estimate one giant joint table."
Because $P(f_i \mid \text{class})$ only involves one feature at a time, each piece can be estimated independently just by counting: for every class, count how often each individual feature value occurs, and normalize. This is precisely why NB training is a single fast counting pass rather than an iterative search — the independence assumption is what makes a closed-form solution possible in the first place.

2. The full posterior is reassembled by multiplying the independent pieces back together.

$$P(\text{class} \mid \text{features}) \propto P(\text{class}) \times P(f_1 \mid \text{class}) \times P(f_2 \mid \text{class}) \times \dots \times P(f_n \mid \text{class})$$

This is the direct algebraic consequence of the independence assumption — the algorithm literally is this formula, applied once per candidate class.

3. Multiplying many small probabilities is numerically unstable, so the algorithm works in log-space instead.
Since probabilities are small fractions, multiplying dozens or hundreds of them together quickly underflows to zero. Taking the log converts every multiplication into an addition, which is exactly why the pseudocode below sums log-priors and log-likelihoods rather than multiplying raw probabilities:

$$\log P(\text{class} \mid \text{features}) \propto \log P(\text{class}) + \sum_{i=1}^{n} \log P(f_i \mid \text{class})$$

4. Classification is just comparing these sums across classes and picking the largest.
Because the denominator $P(\text{features})$ is identical across all classes (it doesn't depend on which class you're testing), it can be dropped entirely — the algorithm only needs to compute the sum above for each class and select the one with the highest value:

$$\hat{c} = \arg\max_{c} \left[ \log P(c) + \sum_{i=1}^{n} \log P(f_i \mid c) \right]$$

So the entire Naive Bayes algorithm — training (counting per-feature statistics) and prediction (summing log-probabilities and taking argmax) — is nothing more than the practical machinery required to exploit the independence assumption. Every design choice in the algorithm (separate per-feature counting, log-space summation, argmax comparison) traces directly back to that single simplifying assumption you introduce with the "≈" in the formula above. This is a good moment to tell students: the assumption isn't a side detail — it's the entire reason the algorithm is simple, fast, and trainable in one pass.

Laplace Smoothing

The counting-based estimation described above has a critical failure mode: what happens when a feature value never appeared in the training data for a given class?

If a word, say "quantum," never appeared in the "spam" class during training, then the raw count-based estimate gives:

$$P(\text{"quantum"} \mid \text{spam}) = \frac{0}{\text{total words in spam}} = 0$$

This single zero is catastrophic because of step 2 above — the likelihoods are multiplied together (or summed in log-space). A single zero-probability feature forces the entire product to zero, regardless of how strongly every other word in the message points toward "spam." In log-space, this is even more visible as a breaking point: $\log(0)$ is undefined (negative infinity), which crashes the summation entirely. In short: one unseen word can override all other evidence and make classification impossible, even when the correct answer is otherwise obvious from the remaining features.

This is a direct consequence of the independence assumption's counting-based estimation — it has no built-in way to express "unlikely but not impossible" for something it simply never observed. Laplace smoothing fixes this by adding a small constant (typically 1) to every count before normalizing, so that no feature ever receives a probability of exactly zero:

$$P(f_i \mid \text{class}) = \frac{\text{count}(f_i, \text{class}) + 1}{\text{total count}(\text{class}) + V}$$

where $V$ is the total number of possible feature values (e.g., vocabulary size). The "+1" in the numerator ensures every feature gets some nonzero probability mass, and the "+V" in the denominator compensates so the probabilities across all features still sum to 1. Effectively, Laplace smoothing encodes a modest, built-in assumption: "even things I've never seen are still possible — just unlikely."

Why this matters practically: without smoothing, a Naive Bayes classifier trained on a finite dataset would be fragile in exactly the scenario it's meant to handle well — real-world text with vocabulary the model hasn't seen before. Smoothing is what makes the counting-based approach robust enough for genuine deployment, and it's a direct patch for the specific failure mode created by the independence assumption's multiplicative structure. (As covered earlier, Laplace is the simplest fix — Lidstone, Good-Turing, Jelinek-Mercer, and Absolute Discounting are more refined alternatives, each addressing shortcomings in how Laplace distributes that extra probability mass.)

Algorithm: The Naive Bayes Implementation

Below is the pseudocode for both the training and prediction phases. Note how the implementation relies on log-space arithmetic to maintain numerical stability and explicitly incorporates the Laplace smoothing constant ($\alpha$) during likelihood estimation.

Training Phase

  1. Function Train_naive_bayes(X_train, Y_train, Num_classes, Num_features):
  2. Initialize Class_counts[num_classes] to 0
  3. Initialize Feature_counts[num_classes][num_features] to 0
  4. Initialize Total_feature_count_per_class[num_classes] to 0
  5. N = Length(X_train)
  6. # ---------- Pass 1: Count Statistics ----------
  7. For i From 0 To N - 1:
  8. C = Y_train[i]
  9. Class_counts[c] = Class_counts[c] + 1
  10. For f From 0 To Num_features - 1:
  11. Feature_counts[c][f] = Feature_counts[c][f] + X_train[i][f]
  12. Total_feature_count_per_class[c] = Total_feature_count_per_class[c] + X_train[i][f]
  13. # ---------- Compute Prior Probabilities ----------
  14. Initialize Log_prior[num_classes] to 0
  15. For c From 0 To Num_classes - 1:
  16. Log_prior[c] = Log(Class_counts[c] / N)
  17. # ---------- Compute Likelihoods With Laplace Smoothing ----------
  18. Initialize Log_likelihood[num_classes][num_features] to 0
  19. Alpha = 1
  20. For c From 0 To Num_classes - 1:
  21. For f From 0 To Num_features - 1:
  22. Numerator = Feature_counts[c][f] + Alpha
  23. Denominator = Total_feature_count_per_class[c] + (Alpha * Num_features)
  24. Log_likelihood[c][f] = Log(Numerator / Denominator)
  25. return log_prior, log_likelihood
  27. # Prediction Phase
  29. Function Predict_naive_bayes(X_test, Log_prior, Log_likelihood, Num_classes, Num_features):
  30. Initialize Class_scores[num_classes] to 0
  31. For c From 0 To Num_classes - 1:
  32. Score = Log_prior[c]
  33. For f From 0 To Num_features - 1:
  34. If X_test[f] > 0:
  35. Score = Score + (X_test[f] * Log_likelihood[c][f])
  36. Class_scores[c] = Score
  37. Predicted_class = Argmax(Class_scores)
  38. return predicted_class
  40. Function Test_naive_bayes(X_test, Y_test, Log_prior, Log_likelihood, Num_classes, Num_features):
  41. Correct_predictions = 0
  42. M = Length(X_test)
  43. For i From 0 To M - 1:
  44. Predicted = Predict_naive_bayes(X_test[i], Log_prior, Log_likelihood, Num_classes, Num_features)
  45. If Predicted == Y_test[i]:
  46. Correct_predictions = Correct_predictions + 1
  47. return correct_predictions / M
