AI Tools for Coding

A hands-on guide to using AI assistants without shipping their mistakes

1. How AI assistants can help you code

A coding assistant (ChatGPT, Claude, GitHub Copilot, Cursor and similar tools) is a language model trained on a large body of code and text. It predicts plausible code from your description. That makes it very fast at routine work, and it is the reason it sometimes produces code that looks right but is not.

Explaining codeWalks through unfamiliar code line by line"Explain this loss-masking snippet and what each tensor shape is."
Boilerplate and scaffoldingArgument parsing, data loaders, config files"Write a PyTorch Dataset for a folder of images with a CSV of labels."
DebuggingReads a stack trace and proposes causes"Here is the traceback and the function. What are the three most likely causes?"

Mental model. Treat the assistant as a fast, well-read junior colleague who never says "I'm not sure." You stay responsible for the specification, the review and the result.

3. Using the tools to produce industry-standard code

"Industry standard" means the code meets the team's rules, not only that it runs: it follows the style guide, is typed and documented, has tests, contains no secrets, has been reviewed by a person, and passes automated checks on every platform you support.

3.1 Set up the environment on Windows and Linux

Windows developers targeting Linux servers should work inside WSL2, so that the code builds and runs where it will be deployed. Native Windows is fine for Windows-targeted software. The commands are almost the same on both:

3.2 Give the tool your standards in a project file

Every tool in Section 2 reads a short instruction file from the repository, so each request starts from your team's rules instead of from nothing. Keep it brief and concrete:

# AGENTS.md  (or CLAUDE.md / .github/copilot-instructions.md)
## Build and test
- Python 3.11. Run: ruff check . && mypy . && pytest -q
- C++20, CMake. Run: cmake -S . -B build && cmake --build build && ctest --test-dir build
## Style
- Type hints on all public functions. Docstrings in Google style.
- Use pathlib for paths. Open text files with encoding="utf-8".
## Rules
- Add or update a pytest test for every behaviour change.
- No new dependencies without asking. Never write secrets or keys into code.
- Code must run on both Linux and Windows.

3.3 A safe working routine

  1. Branch. Start from a clean Git branch so that you can discard everything with one command.
  2. Plan first. Ask the tool for a short plan or a list of files it will change. Correct the plan before it writes code.
  3. One small task at a time. A change you can review in ten minutes is a change you will actually review.
  4. Tests first or together. Have the tests written, confirm they fail for the right reason, then let the tool make them pass.
  5. Approve commands. In agent mode, read each terminal command before it runs. Be especially wary of rm, del, curl ... | sh and anything touching credentials or production.
  6. Read the whole diff (git diff) and run the checks yourself. Do not rely on the tool's statement that the tests pass.
  7. Commit and open a pull request. Ask a colleague to review. The continuous-integration run below is the final gate.

Keep agents away from secrets: do not give them production credentials, exclude files such as .env using the tool's ignore mechanism (for example Cursor's .cursorignore), and prefer a test environment, a container or WSL for anything that executes code.

3.4 Let CI enforce the standard on both platforms

Automated checks do not depend on anyone remembering them. This GitHub Actions workflow runs the same checks on Linux and Windows for every push:

name: ci

jobs:

        os: [ubuntu-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install pytest ruff mypy
      - run: ruff check .
      - run: mypy .
      - run: pytest -q

3.5 Cross-platform mistakes that assistants often make

Assistants write code that works on the system they imagine. Typical failures: hard-coded / path separators, shell commands such as rm -f that do not exist on Windows, files opened without an encoding, and filenames that differ only by case. For example:

import os
def clean(name):
    path = "data/" + name + ".tmp"
    os.system("rm -f " + path)        # fails on Windows, and unsafe if name is untrusted
from pathlib import Path
def clean(name: str) -> None:
    path = Path("data") / f"{name}.tmp"
    path.unlink(missing_ok=True)       # works on Linux and Windows, no shell involved

The Windows runner in the CI workflow above is what catches this class of error automatically.

4. Prompting skills for production-quality code

The quality of generated code depends on how much of the real problem you put into the prompt. Production code needs more than "make it work."

SkillWhat to include
ContextLanguage and version, libraries and versions, the surrounding code, style rules
ContractFunction signature, input types and ranges, return value, which errors are raised and when
Edge casesEmpty input, single element, ties, missing values, class absent from the data, very large input
Non-functional needsTime and memory limits, thread safety, determinism (random seeds), logging, no new dependencies
ExamplesTwo or three input-to-output pairs, including a tricky one you computed by hand
Tests alongsideAsk for tests with the code, or ask for tests first
AssumptionsAsk it to list assumptions and anything it is unsure about
Small stepsOne function or module per request, then integrate

Weak prompt

Write a Python function for macro F1 score.

Strong prompt

Write a Python 3.11 function macro_f1(y_true, y_pred) -> float, standard library only.
- Inputs: two equal-length lists of hashable class labels.
- Raise ValueError if lengths differ or the lists are empty.
- Use the union of labels in y_true and y_pred as the class set.
- If a class has no true positives, its F1 is 0.0 (no ZeroDivisionError).
- Example: y_true=[0,0,1,1], y_pred=[0,2,1,1] -> 5/9 (about 0.5556).
Then: list your assumptions, and write pytest tests including that example
and a case where one class is never predicted.
The strong prompt is a specification. Writing it forces you to understand the problem, which is part of the learning.

5. How judiciously should you use generated code?

UseExamplesGuidance
Use freely, then checkBoilerplate, plotting, file I/O, regex you will test, docstrings, unit-test draftsLow risk, easy to verify by running
Use with careData preprocessing, metrics, training loops, concurrency, anything numericalBugs are silent: the code runs and gives wrong numbers. Verify against an independent reference
Avoid or restrictSecurity, authentication, cryptography, safety-critical logic, code you could not explainUse vetted libraries; have an experienced person review every line
  • Explain-it-back rule. If you cannot explain every line to a classmate, do not merge it.
  • Learn first, then assist. For a concept you are studying (for example backpropagation), write your own version first, then compare with the assistant's. Otherwise you train the tool, not yourself.
  • Protect confidential material. Do not paste secrets, API keys, student or patient data, or proprietary source code into a public tool. Check your organisation's policy.
  • Licensing and integrity. Generated code can resemble licensed code. Follow your course's and employer's rules on disclosing AI assistance.

6. Before deploying: what to do with generated code

  1. Read and explain it. Ask the assistant to explain it too, then check that explanation against the code.
  2. Run static checks. Linters and type checkers (ruff, mypy; clang-tidy for C++), with warnings treated as errors.
  3. Write or review tests. Cover normal cases, edge cases and failure cases. Add a test that cross-checks against a trusted reference library.
  4. Run dynamic checks. Sanitizers for C++ (-fsanitize=address,undefined), profiling for speed and memory, and a fixed random seed for reproducibility.
  5. Scan dependencies and security. Confirm every imported package exists and is the well-known one. Run a vulnerability scan (pip-audit, npm audit). Look for hard-coded secrets and unsanitised input.
  6. Human code review. A second person reviews it as if you had written it yourself.
  7. Continuous integration and staged rollout. Tests run automatically on every change; release to a small group first, with logging and a rollback plan.

7. How to check for hallucinations and errors

A hallucination is output that is fluent and confident but false. In code it appears in four common forms:

TypeExampleHow to catch it
Invented APIA function or parameter that does not existRun it; check the official documentation; help(), dir(), hasattr()
Outdated APIA method removed in the library version you haveCompare against your installed version's documentation
Invented packageA pip install of a name that does not exist, or that an attacker later registersCheck the package on its official index page: maintainer, age, downloads
Plausible but wrong logicOff-by-one, wrong denominator, missing edge caseHand-computed examples, property tests, reference implementations
The most dangerous errors are the ones that run. An invented function crashes immediately and is easy to find. A wrong denominator returns a number that looks reasonable. Test the results, not just whether the code executes.

Techniques that work: run the code on tiny inputs you can compute by hand; compare against an established library on random inputs; ask the assistant to "find bugs in this code" in a fresh conversation; ask it which statements it is least sure of; and always read the official documentation for any API you have not used before.

8. Worked examples

Example A: a metric function that runs but is wrong

Students on this site met macro F1 earlier. The prompt "write a macro F1 function" typically returns something like this:

def macro_f1(y_true, y_pred):
    classes = set(y_true)
    f1s = []
    for c in classes:
        tp = sum(1 for t, p in zip(y_true, y_pred) if t == c and p == c)
        fp = sum(1 for t, p in zip(y_true, y_pred) if t != c and p == c)
        fn = sum(1 for t, p in zip(y_true, y_pred) if t == c and p != c)
        precision = tp / (tp + fp)
        recall = tp / (tp + fn)
        f1s.append(2 * precision * recall / (precision + recall))
    return sum(f1s) / len(f1s)

Reviewing it with the checklist from Section 6 finds three problems:

  • Classes come only from y_true. For y_true=[0,0,1,1], y_pred=[0,2,1,1] it returns 0.833. The class-2 error is silently ignored. The correct macro F1 over classes {0, 1, 2} is 5/9 = 0.556.
  • Division by zero. With y_pred=[0,0,0,0], class 1 is never predicted, so tp + fp = 0 and the function crashes.
  • No input validation. Mismatched lengths are silently truncated by zip.

The corrected version, written after tightening the prompt as in Section 4, uses the identity $F_1 = \dfrac{2\,TP}{2\,TP + FP + FN}$, which avoids the intermediate precision and recall divisions:

def macro_f1(y_true, y_pred):
    if len(y_true) != len(y_pred) or len(y_true) == 0:
        raise ValueError("y_true and y_pred must be non-empty and equal length")
    classes = sorted(set(y_true) | set(y_pred))
    f1s = []
    for c in classes:
        tp = sum(1 for t, p in zip(y_true, y_pred) if t == c and p == c)
        fp = sum(1 for t, p in zip(y_true, y_pred) if t != c and p == c)
        fn = sum(1 for t, p in zip(y_true, y_pred) if t == c and p != c)
        denom = 2 * tp + fp + fn
        f1s.append(2 * tp / denom if denom else 0.0)
    return sum(f1s) / len(f1s)

The tests that catch the original bugs, including a cross-check against scikit-learn on random data:

import random
from sklearn.metrics import f1_score
from metrics import macro_f1

def test_class_only_in_predictions():
    assert abs(macro_f1([0,0,1,1], [0,2,1,1]) - 5/9) < 1e-9

def test_class_never_predicted():
    assert abs(macro_f1([0,0,1,1], [0,0,0,0]) - 1/3) < 1e-9

def test_matches_sklearn_on_random_data():
    rng = random.Random(0)
    for _ in range(200):
        n = rng.randint(1, 50)
        y = [rng.randint(0, 4) for _ in range(n)]
        p = [rng.randint(0, 4) for _ in range(n)]
        assert abs(macro_f1(y, p) - f1_score(y, p, average="macro", zero_division=0)) < 1e-9

Example B: a hallucinated API

Asked for a 7-day moving average and a balanced F1 score, an assistant may suggest:

from sklearn.metrics import balanced_f1_score     # ImportError: no such function
smooth = df["sales"].rolling_mean(7)              # AttributeError: Series has no rolling_mean

Verify before trusting:

python -c "import sklearn.metrics as m; print(hasattr(m, 'balanced_f1_score'))"    # False
python -c "import sklearn.metrics as m; print([n for n in dir(m) if 'f1' in n or 'balanced' in n])"

The second command lists the real names (for example f1_score and balanced_accuracy_score). The moving average is df["sales"].rolling(7).mean(). The older pd.rolling_mean style belongs to a pandas version that has since been removed, which is the "outdated API" case from Section 7. When you hit an error like this, give the exact error message and your library versions back to the assistant.

Example C: undefined behaviour in C++

Request: "Remove all negative numbers from a std::vector<int>." A plausible answer:

#include <vector>

void drop_negatives(std::vector<int>& v) {
    for (auto it = v.begin(); it != v.end(); ++it) {
        if (*it < 0) v.erase(it);      // BUG: erase invalidates 'it'
    }
}

After erase, the iterator it is invalid, and incrementing it is undefined behaviour. The function may even pass a small test and fail in production. It also skips the element that shifts into the erased position. Dynamic checks (Section 6, step 4) find it:

g++ -std=c++20 -g -fsanitize=address,undefined test.cpp && ./a.out

The standard idiom avoids the problem entirely:

#include <vector>
#include <algorithm>

void drop_negatives(std::vector<int>& v) {
    v.erase(std::remove_if(v.begin(), v.end(), [](int x) { return x < 0; }), v.end());
    // C++20 alternative: std::erase_if(v, [](int x) { return x < 0; });
}

Example D: refactoring legacy code safely

Refactoring means changing the structure of code without changing what it does. It is a good job for an assistant, and also a risky one, because the assistant may "improve" behaviour without telling you. The defence is to pin down the current behaviour with tests before any change. Here is a working but hard-to-read function that averages exam scores per department:

# legacy.py
def process(data):
    out = {}
    for i in range(len(data)):
        if data[i]['score'] != None:
            if data[i]['score'] >= 0 and data[i]['score'] <= 100:
                if data[i]['dept'] in out:
                    out[data[i]['dept']].append(data[i]['score'])
                else:
                    out[data[i]['dept']] = [data[i]['score']]
    res = []
    for k in out:
        s = 0
        for v in out[k]:
            s = s + v
        res.append((k, s/len(out[k]), len(out[k])))
    res.sort(key=lambda x: x[1], reverse=True)
    return res

What it does: it keeps scores that are not None and lie between 0 and 100, groups them by department, and returns (dept, mean, count) tuples with the highest mean first. Departments with no valid score do not appear, and ties keep first-appearance order.

Step 1: write characterization tests against the original. They record what the code does today, including the edge cases, and they must pass before you refactor:

import pytest
from legacy import process as old

ROWS = [
    {"dept": "B", "score": 90}, {"dept": "A", "score": 90},
    {"dept": "A", "score": None}, {"dept": "C", "score": 101},
    {"dept": "B", "score": 0},   {"dept": "D", "score": 100},
]

def test_known_case():
    assert old(ROWS) == [("D", 100.0, 1), ("A", 90.0, 1), ("B", 45.0, 2)]

def test_ties_keep_first_appearance_order():
    rows = [{"dept": "Y", "score": 50}, {"dept": "X", "score": 50}]
    assert old(rows) == [("Y", 50.0, 1), ("X", 50.0, 1)]

def test_empty_input():
    assert old([]) == []

Step 2: give the assistant a behaviour-preserving prompt.

Refactor process() in legacy.py into average_by_dept(rows) in scores.py.
Behaviour must not change: same return type (list of (dept, mean, count)),
same ordering including ties, same handling of None and out-of-range scores.
Do not add features or dependencies. Add type hints and a docstring.
Then list every place where behaviour could differ from the original.

Step 3: review the result. After reading it, this is the version we keep:

# scores.py
from collections import defaultdict
from collections.abc import Iterable, Mapping
from typing import Any

def average_by_dept(rows: Iterable[Mapping[str, Any]]) -> list[tuple[str, float, int]]:
    """Return (dept, mean score, count) per department, highest mean first.

    Scores that are None or outside 0..100 are ignored. Departments with no
    valid scores are omitted. Ties keep first-appearance order.
    """
    scores_by_dept: defaultdict[str, list[float]] = defaultdict(list)
    for row in rows:
        score = row["score"]
        if score is not None and 0 <= score <= 100:
            scores_by_dept[row["dept"]].append(score)
    summary = [(dept, sum(s) / len(s), len(s)) for dept, s in scores_by_dept.items()]
    return sorted(summary, key=lambda t: t[1], reverse=True)

It is shorter, typed, documented, and uses names that explain intent. The review is where behaviour changes get caught. Three things to check:

  • Ties. The tie order depends on dict insertion order and on the sort being stable. An assistant that "tidies" this into sorted(..., key=lambda t: (-t[1], t[0])) changes the tie order, and the tie test fails.
  • Floating-point results. Replacing the manual loop with sum(s) / len(s), or the tempting statistics.fmean, can change the last digits of a float mean. On Python 3.12 in a run of 2,000 random inputs, exact comparison mismatched in 14 cases with sum and 27 with fmean. The values agree within a tiny tolerance, and for integer scores they were identical. Compare float results with a tolerance (pytest.approx or math.isclose), and treat a change in numerical method as a separate, deliberate decision.
  • Errors. A row with a missing "score" key raised KeyError before and still does. Silently adding row.get("score") would be a behaviour change.

Step 4: compare old and new on random inputs (differential testing). Point the same tests at both functions, and add a random comparison:

import math, random
import pytest
from legacy import process as old
from scores import average_by_dept as new

@pytest.mark.parametrize("process", [old, new])
def test_known_case(process):
    assert process(ROWS) == [("D", 100.0, 1), ("A", 90.0, 1), ("B", 45.0, 2)]

@pytest.mark.parametrize("process", [old, new])
def test_float_scores_use_tolerance(process):
    rows = [{"dept": "A", "score": s} for s in (0.1, 0.2, 0.3)]
    assert process(rows)[0][1] == pytest.approx(0.2)

def test_old_and_new_agree_on_random_data():
    rng = random.Random(1)
    for _ in range(2000):
        rows = [{"dept": rng.choice("ABC"),
                 "score": rng.choice([None, -1, 101, rng.uniform(0, 100), rng.randint(0, 100)])}
                for _ in range(rng.randint(0, 12))]
        a, b = old(rows), new(rows)
        assert [(d, n) for d, _, n in a] == [(d, n) for d, _, n in b]
        assert all(math.isclose(x[1], y[1], rel_tol=1e-9) for x, y in zip(a, b))

Step 5: finish like any other change. Run ruff check ., mypy . and pytest -q, read the full git diff, and commit the refactoring on its own, separate from any new feature, so a reviewer can see that behaviour did not change. Once the new function is trusted, delete legacy.py and the comparison test. The same discipline works in C++: write characterization tests (for example with GoogleTest or Catch2) first, refactor in small steps, then run clang-tidy and the sanitizers from Section 6.

Summary

  • Tools range from inline completion to agents. Higher autonomy needs more review.
  • Give every tool your standards in a project file, and let CI check them on Linux and Windows.
  • Assistants are fastest for explaining, scaffolding, debugging and drafting tests.
  • Production-quality output needs a specification-quality prompt: context, contract, edge cases, examples, tests.
  • Trust in proportion to how easily the result can be verified. Be most careful with silent numerical errors and security.
  • Before deployment: read, lint, test against a reference, run sanitizers, check dependencies, get a human review.
  • When refactoring, pin current behaviour with tests first, then compare old and new on random inputs.
  • Test the results, not only that the code runs.

Practice exercise

Ask an assistant for a micro F1 function. Without looking at the answer first, write down five edge cases. Then test the generated code against f1_score(..., average="micro") on random data, and list every defect you find.
