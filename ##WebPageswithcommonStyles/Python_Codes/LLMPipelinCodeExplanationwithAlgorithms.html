LLM training pipeline — flowcharts

Sections 1–8 walk the pipeline itself: what flows in and out of each stage, then how each stage works internally. Sections 9–13 are reference material — checkpoint formats and on-disk file layouts — linked to from the sections above wherever they're relevant.

1. Phase 1 — foundation model, data flow

In this phase, A raw text corpus is used to learn a byte-pair-encoding vocabulary (merges) — see Section 3 — and, separately, to pretrain a causal language model on next-token prediction. Pretraining's raw checkpoint(The massive grid of numbers (tensors) representing every attention head, layer, Data like momentum and variance (from AdamW)and embedding in the pre-trained transformer.) is then converted into a HuggingFace-loadable directory. The BPE tokenizer is drawn first because tokenization logically comes before training, but it's a standalone process — this pipeline's actual computation begins at Pretraining, not here. . The model pretraining produces is a transformer — a stack of layers (22 in our sample config), each with its own independent set of weights; nothing is shared or reused across layers the way it would be across time steps in an RNN. See Section 5 for an illustration of this layer/neuron structure.

See Section 9 for what that raw .pt checkpoint actually contains, and Section 10 for how real production pipelines skip it entirely. On "unused": the BPE tokenizer's vocab + merges output isn't dead code — see Section 3 for what it's actually used for — it's just never read back in by anything downstream in this pipeline.

Data Flow Summary:
• Input: Raw multi-gigabyte text corpus.
• Intermediate Outputs: Vocabulary & merge rules (from BPE), raw PyTorch `.pt` model weights checkpoint.
• Final Output: Standardized HuggingFace-compatible directory (`config.json`, `model.safetensors`/`pytorch_model.bin`, tokenizer configs).

2. Phase 2 — alignment, data flow

The pretrained model is completely finished as a raw next-token predictor. It already knows grammar, facts, and language structure. Its saved output is:

  • config.json — architecture details: attention heads, hidden layers, position encoding (exact fields depend on the transformer variant being used).
  • model.safetensors — the actual weights for every layer.

The SFT model starts as an exact copy of the pretrained model. It is not a different architecture or a half-done model — it has the exact same weights right before SFT begins. SFT is simply a phase shift in the training objective:

  • Pretraining objective: predict the very next word on indiscriminate internet text.
  • SFT objective: predict the next word specifically in a conversational turn, acting as a helpful assistant.
  • The prompt / assistant-response pair from the SFT dataset is concatenated into a single continuous sequence for attention context, and training is performed while masking the prompt tokens.
  • [Prompt Tokens] + [Response Tokens] is fed into the model. The self-attention layers compute attention across both parts so the model fully understands the question being asked.
  • The SFT training outputs a checkpoint that contains the finalized, optimized model weights (the knowledge), but it has stripped away the heavy training states (like optimizer buffers) that were used to get there. The key difference is that while the Pretraining checkpoint only knew how to autocomplete text, the SFT checkpoint has been re-calibrated through instruction-tuning to act like a helpful assistant.
  • Why concatenate (the attention context): Transformers use self-attention, meaning every token looks at all preceding tokens. For the model to generate a smart response, it must read and understand the prompt first. By putting [User Prompt] + [Assistant Response] in the same sequence, the assistant's tokens can mathematically "attend to" the user's prompt tokens and understand what question is being asked.
  • Why mask the prompt (the loss control): If loss were calculated on the user's prompt, the model would waste gradient steps learning how to mimic how users ask questions, rather than learning how to answer them. Setting prompt token labels to -100 tells the optimizer: let the model read the prompt to gather context, but don't update any weights based on how well it predicts the prompt's words — only update weights based on how accurately it generates the response.

In reward modeling:

  • The preference pairs (chosen vs. rejected responses), alongside the SFT checkpoint, train a separate model to act as a judge.
  • Result: a frozen reward model that can score how good any given response is.

Finally, in PPO / RLHF (final alignment):

  • Raw prompts only are fed in. The SFT checkpoint acts as the starting policy, and the frozen reward model grades its answers.
  • Using reinforcement learning, the model is adjusted so it learns to generate high-scoring, safe responses.

Result: the final aligned policy checkpoint — your production-ready chat model.

See Section 5 for exactly how the pretrained checkpoint gets loaded at the start of SFT, and Section 13 for the full masking mechanics.

Data Flow Summary:
• Inputs: Supervised instruction datasets (Prompt + Response pairs), Preference datasets (Chosen vs. Rejected response pairs), and standalone prompts.
• Intermediate Outputs: SFT Policy checkpoint, frozen Bradley-Terry Reward Model weights.
• Final Output: Fully aligned chatbot policy checkpoint optimized via reinforcement learning.

3. BPE tokenizer — internals

The corpus is split into characters with an end-of-word marker and word frequencies are counted. A loop then repeatedly counts adjacent symbol-pair frequencies and merges the single most frequent pair into a new symbol, until vocab_size is reached. The result is the final vocabulary plus the ordered list of merges, used later to encode/decode new text — the tokenizer does use its own vocab and merges internally, that's exactly what its own encode()/decode() methods operate on, so this isn't dead code within this file. It's "unused" only in the narrower sense that nothing downstream in this pipeline (pretraining, SFT, RM, PPO) ever loads this particular saved vocab/merges file back in — see Section 1.

Data Flow Summary:
• Input: Raw training corpus strings.
• Intermediate Output: Frequency tables of adjacent character and subword pairs updated iteratively.
• Final Output: Token dictionary mapping integer IDs to subword strings, plus sequential merge rules.

4. Pretraining — internals

Streaming corpus data and the tokenizer feed a training step: forward pass computes next-token loss, then backward pass and an AdamW step (with gradient clipping and a cosine schedule) update the model. This repeats until max_steps, with checkpoints written periodically as a raw torch.save state dict.

Data Flow Summary:
• Inputs: Tokenized text chunks represented as integer tensor batches.
• Intermediate Output: Scalar cross-entropy loss values computed across predicted token probabilities.
• Final Output: Raw PyTorch state-dictionary checkpoint files containing trained transformer weights (`.pt`).

5. How SFT loads the pretrained model

SFT doesn't build a new model — it opens the exact same HF-format directory pretraining (via conversion) produced, and continues training those same weights under a new objective. AutoModelForCausalLM.from_pretrained(config.model_name) reads config.json to reconstruct the architecture, then loads the safetensors weights into it in memory. From that point on it's the same object being fine-tuned, not a new one being built from scratch — see Section 13 for exactly why the masked-loss training step then works the way it does.

That middle box, "Load + fine-tune," is really two things happening back-to-back rather than one. First it's a plain load: the architecture is rebuilt from config.json and the pretrained weights are copied in — a one-time step, no different from loading any other HF checkpoint. Then training takes over: none of those weights are frozen, so the SFT loop (Section 6) runs its usual forward pass, masked loss, and backward step directly on top of them, epoch after epoch, gradually specializing weights that already encode general language ability rather than learning language from nothing. See Section 1 for an illustration of this layer/neuron structure — the exact same weights described in Section 9's model.safetensors.

6. SFT — internals

Prompt-response JSONL pairs are tokenized into a single sequence, with prompt tokens masked to IGNORE_INDEX in the labels. A training step then computes loss only on the response tokens and updates weights, repeating each epoch, producing a final SFT checkpoint in HF format. The diagram below shows this token by token: prompt tokens (P1–P3) flow through the network for context but their predictions are skipped; response tokens (R1–R2) flow through the same network and their predictions are scored.

Data Flow Summary:
• Inputs: Structured instruction pairs (User Prompt + Assistant Response text formatting).
• Intermediate Output: Masked token tensors where prompt gradients are ignored (label = -100).
• Final Output: HuggingFace-compatible SFT model directory.

skip = prediction computed but excluded from the loss (label = -100, from Section 13's gradient masking). score = prediction included in the loss and contributes to the backward pass. All five tokens still pass through every layer either way — masking only affects which predictions count toward the loss, not which tokens get processed.

7. Reward model — internals

Each preference pair (chosen, rejected) is scored by a shared transformer backbone plus a linear reward head, reading the scalar at the last non-padding token. The Bradley-Terry pairwise loss, -log(sigmoid(r_chosen - r_rejected)), is backpropagated, repeating over all pairs, to produce a frozen reward-model checkpoint.

Data Flow Summary:
• Inputs: Human preference datasets containing a prompt paired with two competing responses (Chosen vs. Rejected).
• Intermediate Output: Scalar reward scores (r_chosen and r_rejected) evaluated through the Bradley-Terry log-sigmoid loss function.
• Final Output: Frozen reward model checkpoint file (`reward_model.pt`).

8. PPO / RLHF — internals

For each batch of prompts: the policy generates a rollout response, the frozen reward model scores it, a per-token KL penalty against the reference (SFT) model is subtracted so the policy can't drift too far, a value head estimates an advantage baseline (GAE) to reduce gradient variance, and a clipped PPO surrogate objective updates the policy. This repeats for the next batch of prompts.

Data Flow Summary:
• Inputs: Unlabeled prompt text batches, initial SFT reference model, and frozen Reward Model.
• Intermediate Outputs: Generated model rollouts, scalar reward ratings, token-level KL divergence metrics, and Generalized Advantage Estimations (GAE).
• Final Output: Final fine-tuned PPO Aligned Policy Checkpoint.

9. What is a "raw checkpoint (.pt)"?

A .pt file is just PyTorch's save format — under the hood it's a Python dictionary, pickled to disk. When llm_pretraining.py checkpoints, it saves the model's weights (state_dict) bundled together with the optimizer's state, the LR scheduler's state, and the current step number, so training can resume exactly where it left off. What it does not save is any description of the architecture — no layer count, no hidden size, nothing. So to load it back, something has to already know the exact shape of the model it was saved from and rebuild that shape first. That's the one job convert_pre_trained.py does: it reconstructs the same GPT2Config/GPT2LMHeadModel architecture from the flags you pass it, pours the raw weights into it, then calls save_pretrained() — which writes a self-describing directory that any tool can load with no prior knowledge. (Referenced from Section 1.)

10. Production checkpointing — no raw .pt

The raw-.pt-then-convert step exists here because llm_pretraining.py is a minimal, single-file teaching script that hand-rolls its own torch.save() checkpointing. Real production training loops don't do this. Frameworks like HuggingFace Trainer/Accelerate or DeepSpeed checkpoint using save_pretrained() directly, so every checkpoint is already a self-describing HF-format directory — there's no separate raw dict and no conversion step. Large-scale training does still keep a second, engineering-only checkpoint format: a sharded training-state snapshot (via FSDP or DeepSpeed ZeRO) that includes optimizer state, split across GPUs, purely so an interrupted run can resume fast. That sharded snapshot is never handed to SFT/RM/PPO or shipped anywhere — it's consolidated into one HF-format checkpoint whenever a release/eval checkpoint is needed, and that's the artifact the rest of the pipeline actually consumes. (Referenced from Section 1.)

Data Flow Summary:
• Input: Model + optimizer state, sharded across GPUs during distributed training.
• Intermediate (engineering-only): Sharded resume checkpoint (FSDP/DeepSpeed ZeRO) — for resuming an interrupted run, never used downstream.
• Final Output: HF-format checkpoint written directly via save_pretrained() — the same format every downstream stage (SFT, RM, PPO) expects.

12. Vocab & Merges — The Tokenizer Foundation

These files define the translation layer between human language and the integer vectors the model processes. They are the primary output of the BPE Training stage.

The Components:
• vocab.json: A master map assigning every unique subword token to a unique integer ID (e.g., "hello": 4512).
• merges.txt: The sequential "rulebook" of merges performed during BPE training. It tells the tokenizer how to combine individual characters into frequent subwords (e.g., h e -> he).
Sample: vocab.json (Simplified)
{
  "<|end_of_text|>": 0,
  "the": 1,
  "ing": 2,
  "hello": 3,
  "world": 4
}
Sample: merges.txt (Rulebook)

13. SFT Mechanics & Architecture Mapping

Core architectural and methodological details regarding how Supervised Fine-Tuning interacts with pretrained models, configuration files, and sequence gradient masking. (Referenced from Section 2 and Section 5.)

Key Architectural Principles:
• Exact Model Architecture (config.json): Pretrained binary weights (`.safetensors`) are meaningless raw numbers on their own. The config file supplies the precise neural network blueprint (layers, dimensions, attention heads) required for PyTorch to instantiate the architecture correctly.
• Model State at SFT Start: An SFT model is not half-done or structurally different; it begins as an exact clone of the fully pretrained foundation model. Only the training objective changes (shifting from indiscriminate next-token continuation to instruction response modeling).
• Prompt + Response Concatenation: Sequences are concatenated into `[User Prompt] + [Assistant Response]` so the model can read the prompt and build contextual self-attention over it before generating text.
• Gradient Masking (IGNORE_INDEX = -100): While the prompt is fed in for attention context, its label IDs are set to -100. This instructs the cross-entropy loss function to completely ignore prompt tokens, ensuring weight updates focus exclusively on training the model to answer correctly.
